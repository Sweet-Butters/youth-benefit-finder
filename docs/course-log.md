# 강의용 기록: AI와 함께 서비스 기획하고 만들기

> 이 저장소를 만든 과정을 나중에 강의로 옮기기 위한 기록이다. **무엇을 만들었는지**보다 **어떻게 정했고, 무엇이 틀렸고, 어떻게 잡았는지**를 남긴다.
> 저장소가 공개라 팀원 이름과 개인정보는 쓰지 않는다. 역할은 "사용자(PM)", "Claude", "에이전트"로 적는다.

## 기록이 남는 곳

| 어디 | 무엇 | 강의에서 쓰는 법 |
|---|---|---|
| 이 문서 | 세션별 이야기: 목표, 결정, 실수와 교정, 다시 쓸 프롬프트 | 강의 흐름의 뼈대 |
| `docs/decisions.md` | 결정 D1~와 **이유** | "왜 이렇게 정했나" 슬라이드 |
| `docs/progress.md` | 시각별 로그 (누가, 무엇을) | 타임라인 |
| GitHub PR 설명 | 변경마다 무엇을, 왜, 어떻게 확인했나 | 단계별 결과물 |
| git 기록 | 파일이 어떻게 바뀌었나 | 전후 비교 |
| 일일 작업 로그 (저장소 밖, 사용자 PC) | 하루 전체의 "사용자가 한 일 / AI가 한 일" | 세션 회고 |
| 대화 원본 (저장소 밖, 사용자 PC) | 실제 주고받은 말 | 인용, 데모 재현 |

## 세션 1 · 2026-09-25 · 기획을 처음부터 다시 짜다

**목표**: "청소년 혜택 찾기" 아이디어를 실제로 만들 수 있는 기획으로 바꾼다.

**흐름**
1. 머메이드로 기획 로드맵 그리기 → Codex 에이전트에게 그림으로 옮기게 함 → 나중에 "머메이드로 충분하다"며 그림 삭제.
2. 개인 스킬(현황판, 마감, PR, 검증)을 프로젝트에 설치. 현황판(`progress.md`, `active-work.json`, `decisions.md`)이 이때 생김.
3. "비판적으로 평가해 줘" → AI가 약점 지적 → 사용자가 "이거 다 추론 아닌가?"라고 되물음.
4. **사용자가 서비스의 본질을 직접 정의**: "청소년은 진로 고민이 많다, 이야기하고 방향을 제시해 줄 곳이 필요하다." → 사람 중심 진로 대화 + AI 보조 (D6).
5. MVP 범위를 사용자가 정함: 멘토 매칭이 아니라 **사람 모으기가 1차 목표** (D7). "대학 없이"를 앞세우지 않기로 함 → 한 줄 소개 "지금 내 자리에서 시작하는 진로".
6. 커리큘럼이 아니라 **지도** (D8), 소셜벤처 (D9), 데이터 원칙 (D10), 가입 (D11~D13), 커뮤니티는 Q&A부터 (D12), 관심 퀴즈 (D14), 나의 기록 (D15).
7. 텀블벅·공모전·지원사업 조사 → `funding.md`, 수익 모델 → `business-model.md`.
8. 동아리 1주차 미션 PPT를 사용자 양식 그대로 채움.

**실수와 교정 (강의 핵심)**
| 무엇이 틀렸나 | 어떻게 잡았나 | 교훈 |
|---|---|---|
| AI가 "같이 고민해 줄 어른이 없다"를 문제 정의에 씀. 근거 없음 | 사용자가 "validation 해줘, 이거 맞아?"라고 요구 | AI의 그럴듯한 문장은 추론일 수 있다. 출처를 요구하라 |
| 2023 실태조사 수치를 씀. 2025 조사가 이미 나와 있었음 | 두 번째 검증 요구에서 발견 | "최신 자료인가"를 따로 물어라 |
| "커리어넷은 학교 중심" → 틀림 (개인 검사 가능) | 같은 검증에서 발견 | 한 줄 요약에 숨은 오류가 많다 |
| 한 기사의 수치가 조사와 맞지 않았음 | 두 곳 이상 대조 | 수치는 두 출처로 확인 |
| 연구원(2025) 결과가 우리 문제 정의와 일부 다름 (69.5%가 진로 계획을 세운 적 있음) | 논문 조사 중 발견, 숨기지 않고 문서에 표시 | 반대 근거도 기록하라 |

**다시 쓸 프롬프트**
- "이 프로젝트 어떻게 기획했으면 좋겠어? 머메이드 문법으로"
- "비판적으로 & 중립적으로"
- "이거 다 추론 아닌가?" / "이 문장도 정말이야?"
- "이거 validation 해줘, 아까 했을땐 오류 많았잖아"

## 세션 2 · 2026-09-25 저녁 ~ 09-26 · 설계와 1주차 개발

**목표**: 기획을 코드로 옮길 설계를 정하고, 첫 기능을 만든다.

**흐름**
1. 나의 기록(포트폴리오) 아이디어 → **에이전트에게 기존 서비스·법 조사를 맡김** (e청소년이 이미 비슷한 것을 제공한다는 사실 발견) → 차별점을 좁힘 (D15).
2. 아키텍처 설계는 **Fable 에이전트에게 맡기고** Claude가 검토. 설계 중에 D16~D19가 정해져 검토 메모로 차이를 적음 (트랙을 `learner`/`supporter`로).
3. 사용자가 전체 비전을 말함: 탐색 → 당근(지원 추천) → 기록·보증 → 취업 연계 → 20대 이상 확장 (D16~D19).
4. "데이터를 최대로 모으고 싶다, 개인정보도" → 행동 데이터 최대는 D20으로, **개인정보 확대는 법률 검토가 필요해 결정 대기**로 분리.
5. B2G·B2B 데이터 수요 조사(에이전트) → `data-strategy.md`.
6. 1주차 개발: 데이터 형식, 요리사 초안, 자동 검사, Astro 뼈대, CI.

**실수와 교정**
| 무엇이 틀렸나 | 어떻게 잡았나 | 교훈 |
|---|---|---|
| 설계 문서가 이미 쓴 결정 번호(D16, D17)를 새로 제안함 | 검토에서 발견, D20~로 옮김 | 병렬로 일하면 번호·이름이 부딪힌다 |
| 트랙이 "학생/어른"이라 20대 이상 진로 탐색자가 들어갈 곳이 없었음 | D19와 대조 검토 | 설계는 **나중 계획**과 대조해 검토하라 |
| 요리사 데이터에서 길 ID와 단계 ID가 겹침 | **방금 만든 자동 검사가 첫 실행에서 잡음** | 검사를 먼저 만들면 첫날부터 값을 한다 |
| 스키마의 정규식 escape가 깨짐 | 검사 실행 오류 | 셸로 JSON 쓸 때 escape 주의 |

**다시 쓸 프롬프트 / 에이전트 설정**
- 설계를 더 강한 모델에게 맡기고 현재 모델이 검토: "바꾸기 어려운 결정만, 2쪽 안팎, 결정과 어긋나면 '재검토 제안'으로"
- 조사 에이전트 지시의 공통 규칙: "확인됨 / 추측 / 확인 못함을 항목마다", "수치는 두 출처", "파일은 만들지 말고 결과만"

## 세션 3 · 2026-09-26 · 요리사 완성본 (진행 중)

**목표**: 기능을 다 만들기보다, **요리사 분야 하나를 끝까지 채운 완성본**을 만들어 봉사 수업에서 보여 준다.

**왜 이렇게 정했나**: "지금 바로 MVP 사이트를 만들면 만족스러울까?"라는 사용자 질문에, 코드는 금방이지만 **내용(도움 정보, 글)이 비어 텅 빈 지도**가 된다고 답함. 그래서 한 분야를 완성품처럼.

**작업 방식: 병렬**
| 작업 | 누가 | 파일 |
|---|---|---|
| 디자인 다듬기, 글 페이지 틀 | Claude (이 세션) | `web/src/layouts`, `pages` |
| 요리사 도움 정보 **후보** 조사 (5~10개) | 에이전트 A | `data/candidates/cooking-helps.md` (사이트에 안 올림) |
| 글 초안 "요리사가 되는 여러 길" | 에이전트 B | `web/src/content/guide/cooking-paths.md` |

- 병렬 규칙: 파일이 겹치지 않게 나누고, 합치는 사람은 한 명(Claude). 진짜 병목은 만드는 속도가 아니라 **사람이 확인하는 속도**라 후보는 5~10개로 제한.
- 다 만든 뒤 **Fable에게 검토**를 맡길 예정: 17살 학교 밖 청소년의 눈, 사실 일치, 첫인상.
