# 강의용 기록: AI와 함께 서비스 기획하고 만들기

> 이 저장소를 만든 과정을 나중에 강의로 옮기기 위한 기록이다. **무엇을 만들었는지**보다 **어떻게 정했고, 무엇이 틀렸고, 어떻게 잡았는지**를 남긴다.
> 저장소가 공개라 팀원 이름과 개인정보는 쓰지 않는다. 역할은 "사용자(PM)", "Claude", "에이전트"로 적는다.

## 기록이 남는 곳

| 어디 | 무엇 | 강의에서 쓰는 법 |
|---|---|---|
| 이 문서 | 세션별 이야기: 목표, 결정, 실수와 교정, 다시 쓸 프롬프트 | 강의 흐름의 뼈대 |
| `docs/decisions.md` | 결정 D1~와 **이유** | "왜 이렇게 정했나" 슬라이드 |
| `docs/progress.md` | 시각별 로그 (누가, 무엇을) | 타임라인 |
| GitHub PR 설명 | 변경마다 무엇을, 왜, 어떻게 확인했나 | 단계별 결과물 |
| git 기록 | 파일이 어떻게 바뀌었나 | 전후 비교 |
| 일일 작업 로그 (저장소 밖, 사용자 PC) | 하루 전체의 "사용자가 한 일 / AI가 한 일" | 세션 회고 |
| 대화 원본 (저장소 밖, 사용자 PC) | 실제 주고받은 말 | 인용, 데모 재현 |

## 세션 1 · 2026-09-25 · 기획을 처음부터 다시 짜다

**목표**: "청소년 혜택 찾기" 아이디어를 실제로 만들 수 있는 기획으로 바꾼다.

**흐름**
1. 머메이드로 기획 로드맵 그리기 → Codex 에이전트에게 그림으로 옮기게 함 → 나중에 "머메이드로 충분하다"며 그림 삭제.
2. 개인 스킬(현황판, 마감, PR, 검증)을 프로젝트에 설치. 현황판(`progress.md`, `active-work.json`, `decisions.md`)이 이때 생김.
3. "비판적으로 평가해 줘" → AI가 약점 지적 → 사용자가 "이거 다 추론 아닌가?"라고 되물음.
4. **사용자가 서비스의 본질을 직접 정의**: "청소년은 진로 고민이 많다, 이야기하고 방향을 제시해 줄 곳이 필요하다." → 사람 중심 진로 대화 + AI 보조 (D6).
5. MVP 범위를 사용자가 정함: 멘토 매칭이 아니라 **사람 모으기가 1차 목표** (D7). "대학 없이"를 앞세우지 않기로 함 → 한 줄 소개 "지금 내 자리에서 시작하는 진로".
6. 커리큘럼이 아니라 **지도** (D8), 소셜벤처 (D9), 데이터 원칙 (D10), 가입 (D11~D13), 커뮤니티는 Q&A부터 (D12), 관심 퀴즈 (D14), 나의 기록 (D15).
7. 텀블벅·공모전·지원사업 조사 → `funding.md`, 수익 모델 → `business-model.md`.
8. 동아리 1주차 미션 PPT를 사용자 양식 그대로 채움.

**실수와 교정 (강의 핵심)**
| 무엇이 틀렸나 | 어떻게 잡았나 | 교훈 |
|---|---|---|
| AI가 "같이 고민해 줄 어른이 없다"를 문제 정의에 씀. 근거 없음 | 사용자가 "validation 해줘, 이거 맞아?"라고 요구 | AI의 그럴듯한 문장은 추론일 수 있다. 출처를 요구하라 |
| 2023 실태조사 수치를 씀. 2025 조사가 이미 나와 있었음 | 두 번째 검증 요구에서 발견 | "최신 자료인가"를 따로 물어라 |
| "커리어넷은 학교 중심" → 틀림 (개인 검사 가능) | 같은 검증에서 발견 | 한 줄 요약에 숨은 오류가 많다 |
| 한 기사의 수치가 조사와 맞지 않았음 | 두 곳 이상 대조 | 수치는 두 출처로 확인 |
| 연구원(2025) 결과가 우리 문제 정의와 일부 다름 (69.5%가 진로 계획을 세운 적 있음) | 논문 조사 중 발견, 숨기지 않고 문서에 표시 | 반대 근거도 기록하라 |

**다시 쓸 프롬프트**
- "이 프로젝트 어떻게 기획했으면 좋겠어? 머메이드 문법으로"
- "비판적으로 & 중립적으로"
- "이거 다 추론 아닌가?" / "이 문장도 정말이야?"
- "이거 validation 해줘, 아까 했을땐 오류 많았잖아"

## 세션 3 · 2026-09-26 · 요리사 완성본 (진행 중)

**목표**: 기능을 다 만들기보다, **요리사 분야 하나를 끝까지 채운 완성본**을 만들어 봉사 수업에서 보여 준다.

**왜 이렇게 정했나**: "지금 바로 MVP 사이트를 만들면 만족스러울까?"라는 사용자 질문에, 코드는 금방이지만 **내용(도움 정보, 글)이 비어 텅 빈 지도**가 된다고 답함. 그래서 한 분야를 완성품처럼.

**작업 방식: 병렬**
| 작업 | 누가 | 파일 |
|---|---|---|
| 디자인 다듬기, 글 페이지 틀 | Claude (이 세션) | `web/src/layouts`, `pages` |
| 요리사 도움 정보 **후보** 조사 (5~10개) | 에이전트 A | `data/candidates/cooking-helps.md` (사이트에 안 올림) |
| 글 초안 "요리사가 되는 여러 길" | 에이전트 B | `web/src/content/guide/cooking-paths.md` |

- 병렬 규칙: 파일이 겹치지 않게 나누고, 합치는 사람은 한 명(Claude). 진짜 병목은 만드는 속도가 아니라 **사람이 확인하는 속도**라 후보는 5~10개로 제한.
- 다 만든 뒤 **Fable에게 검토**를 맡길 예정: 17살 학교 밖 청소년의 눈, 사실 일치, 첫인상.

**결과 (2026-09-26)**
- 에이전트 B (글 초안): 네 길, 한식조리기능사 한눈에, 이번 주 할 일. 출처 4개(큐넷 2, 교육청, 생활법령). 수수료·세부 조건은 일부러 뺐다.
- 에이전트 A (도움 후보): 공식 페이지로 확인한 후보 9개, 뉴스로만 본 후보는 따로. 대학 진학 단계는 후보를 못 찾음. 꿈드림 전국 사이트가 인증서 만료로 접속되지 않아 대체 출처를 씀.
- Claude (디자인): 헤더·홈·분야 지도·글 목록을 다듬음. "채워 둘게요" 문구를 단계마다 → 길마다 한 번으로.
- Fable 검토에서 나온 상위 5개와 처리:
  1. **초안은 실제 빌드에서 사라진다** → 글 공개 여부는 팀 결정으로 남김 (지금은 초안, 개발 서버에서만 보임)
  2. 홈이 "도움을 챙겨요"라고 약속하는데 도움 0개, 같은 안내 4번 반복 → 안내를 페이지 위 한 곳으로 합치고 날짜 표시, 홈 문구를 "적을 거예요"로
  3. 모바일에서 같은 단계가 4번씩 반복 → 앞 길에서 본 단계는 접기(펼쳐 보기). 모바일 길이 3,855px → 약 3,100px
  4. 첫 화면에 "왜 요리사?"가 없고 눌리지 않는 버튼 → "요리사부터 볼게요"와 "3분이면 봐요 · 가입 없이" 한 줄, 준비 중 버튼 제거
  5. 도움의 지역·마감·나이·비용을 그릴 자리가 없음, "무료 강의" 라벨이 유료 강좌에 거짓이 됨 → 칩으로 표시, 라벨을 "강좌·훈련"으로, `resource`(자료) 종류 추가
- 그 밖에: 큐넷 딥링크, 응시 자격 문구 통일, 길 지도 제목을 "요리사 길 지도"로 바꿔 글 제목과 구분, 불러오지 않던 글꼴 지정 제거, 초록 점 범례.

**실수와 교정**
| 무엇이 틀렸나 | 어떻게 잡았나 | 교훈 |
|---|---|---|
| 모바일 스크린샷이 잘려 보여 레이아웃 오류로 오해할 뻔함 | 브라우저 실제 폭을 찍어 보니 390이 아니라 518px. Playwright로 폰 화면을 흉내 내 가로 넘침 0px 확인 | **검사 도구 자체를 먼저 의심하라.** 눈으로 본 것과 측정한 것을 구분 |
| 글 초안의 두 표현이 출처보다 강함 ("60점 넘은", "넘겨 일할 수 없어요") | Claude가 출처 문장과 대조 | 에이전트가 쓴 글도 출처와 한 줄씩 대조 |
| 데이터 문장은 '~다', 화면은 '~요'라 말투가 섞임 | 화면을 보고 발견 | 콘텐츠 말투는 처음에 정해 두기 |
| 화면을 개발 서버로만 확인해, 실제 빌드에서 초안 글이 사라지는 것을 놓침 | Fable 검토가 코드를 읽고 지적 | **실제로 배포될 결과물로 확인하라** |
| 도움 항목의 지역·비용을 화면에 안 그려, 지역 사업이 전국 사업처럼 보일 뻔함 | Fable이 후보 파일과 화면 코드를 대조 | 데이터에 있는 조건은 화면에도 보여야 한다 |

**다시 쓸 프롬프트 / 에이전트 설정**
- 병렬 작업 지시에 넣은 규칙: "이 파일 하나만 만든다, 다른 파일은 건드리지 않는다, 커밋하지 않는다"
- 사실 조사 규칙: "원문에 없으면 '원문에 없음'이라고 쓴다, 뉴스만 있는 건 따로 적는다"
- 검토 에이전트(Fable): "17살 학교 밖 청소년의 눈 / 사실·일치 / 디자인 첫인상, 확실과 의견을 나눠서"

## 세션 4 · 2026-09-26 · AI 디자인이 다 비슷하다

**계기**: 사용자가 "AI들은 약속한 듯이 디자인이 통일되어 있다, 마음에 안 든다"고 함. 실제로 첫 디자인은 전형이었다(주황 버튼, 둥근 카드, 알약 태그, 가운데 큰 제목).

**왜 그런가**: 방향을 주지 않으면 AI는 가장 흔한 스타트업 랜딩으로 수렴한다.

**대응**
1. 꾸미기가 아니라 **서비스 안의 은유**에서 콘셉트를 찾는다: "길 지도" → 지하철 노선도 (길 = 노선, 단계 = 역, 공유 단계 = 환승역).
2. 레퍼런스를 먼저 찾고, 흔한 패턴을 **금지 목록**으로 준다.
3. 한 안을 다듬지 말고 **완전히 다른 시안 3개**를 병렬로 만들어 비교한다. 가능하면 학생이 고른다.

**시안 3개 (에이전트 3개 병렬, 같은 실제 데이터)**
| 시안 | 핵심 | 공유 단계 반복 문제를 푸는 방식 |
|---|---|---|
| 1. 지하철 노선도 | 노선 4개, 역 8개, 환승역. 역을 누르면 승강장 표지판처럼 앞 역·다음 역 | 역이 한 번만 나온다 (환승역) |
| 2. 다꾸 스크랩북 | 종이·테이프·스티커·손글씨 메모, 레시피 카드 | 같은 스티커, 두 번째부터 작게 |
| 3. 대화형 | 선배가 한 번에 하나씩 묻고 "이 길부터 봐도 좋아요" | 한 번에 한 길만 보여 준다 |

**실수와 교정**
| 무엇이 틀렸나 | 어떻게 잡았나 | 교훈 |
|---|---|---|
| 시안 3 맨 위에 제목 글자가 페이지에 새어 나옴 | 세 시안을 나란히 놓고 한 번에 봄 | Astro `<title>`에 식 + 쉼표 텍스트를 섞으면 깨진다. 템플릿 문자열로 한 덩어리로 |

**다시 쓸 프롬프트**
- 시안 지시의 공통 규칙: "자기 HTML 문서로 (기존 레이아웃 쓰지 말 것)", "금지: 가운데 히어로+회색 부제+주황 버튼, 같은 둥근 카드 격자, 알약 태그, 그라데이션, 이모지", "390px 가로 넘침 0, JS 오류 0을 직접 스크린샷으로 확인"

**합친 시안 (시안 4, D22)**: 사용자가 "3과 1을 짬뽕하고, 혜택이 자동으로 옆에 나왔으면, 이게 당근"이라고 함.

## 세션 6 · 2026-09-26 · 혜택을 어떻게 효율적으로 모을까

**계기**: 사용자가 "혜택 같은 걸 어떻게 효율적으로 찾아서 모을지 모르겠다, 찾아보고 공모전 레이더(같은 팀의 다른 프로젝트)의 장점만 흡수해 달라"고 함.

**병렬**: 에이전트가 공식 데이터 경로(API·파일)를 조사하는 동안 Claude가 공모전 레이더 저장소를 직접 읽음.

**결과** (`docs/collection-strategy.md`)
- data.go.kr 키 하나로 대부분: 보조금24(연령 코드 있음, 수정일시로 증분), 장학재단 CSV(월간), 청소년 활동·자원봉사 API, 큐넷 시험일정.
- 막힌 곳: 내일배움카드 훈련과정 API는 **기업회원만** 키 발급 → 링크로 대신. 민간 공모전 사이트는 약관상 재게시 불가 → 제목·링크만. 꿈드림·교육청은 피드 없음 → 사람.
- 공모전 레이더에서 가져온 것: 매일 GitHub Actions, 출처별 모듈과 건강 기록, robots.txt 매번 확인, 규칙 먼저 + AI는 확신할 때만, 캐시와 비용 기록, 중복 합치기, 날짜로 상태 계산, 정답 라벨로 정확도 평가.
- 새로 정할 것: 정부 공식 API에서 자동으로 받은 항목을 사람 확인 없이 보여 줄지 (`auto-publish`).

**교훈**
- 크롤링부터 떠올리기 쉽지만, **공식 API를 먼저 찾으면** 법·약관 걱정과 유지보수가 크게 준다.
- 이미 만든 프로젝트는 좋은 레퍼런스다. 코드보다 **운영 방식**(건강 기록, 평가, 캐시)을 가져오는 게 값지다.
